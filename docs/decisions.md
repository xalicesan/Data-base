# Решения по модели данных

Зафиксированные договорённости (вариант 4.10).

## Предметная область

- Оранжевый блок на ER-схеме — **организатор**, красный — **спортивное сооружение**.
- Разряды: 3-й — низший (level = 1), 2-й (level = 2), 1-й (level = 3).
  В БД хранится числовой `rank.level`, чтобы работало «не ниже разряда».
- Клуб имеет ровно один вид спорта; спортсмен состоит в одном клубе,
  но может тренироваться у тренеров других клубов и заниматься 1–2 видами спорта.
- Вид спорта спортсмена не хранится отдельно: выводится из клуба его тренеров.
- Оборудование — не отдельная сущность, а атрибуты подтипа сооружения
  (`ring_size`, `tower_max_m`, `has_net`, `has_hoop`).
- Допустимость вида спорта на сооружении проверяется по оборудованию:
  бокс — ринг, дзюдо/борьба — мягкое покрытие, ПСВ — вышка, баскетбол — кольцо,
  волейбол — сетка. Поэтому ПСВ нельзя проводить в Б3 (вышек нет).
- «Мероприятие» — отдельная сущность: одно место, одна дата, один организатор,
  несколько соревнований по разным видам спорта.

## Данные

- Даты соревнований — 2025 год, как в исходных материалах.
- Призовые места присвоены по порядку перечисления победителей (1, 2, 3).
- В соревновании по волейболу победитель 51 — опечатка, исправлено на 53.
- ФИО спортсменов придуманы для учебного задания; ФИО организаторов также
  сгенерированы. Совпадения с реальными людьми случайны.
- Списки «не участвовали» из исходных данных в БД не хранятся:
  запрос 11 получает их через `NOT EXISTS`.

## Архитектура

- DFD-сущности «зрители», «бюджет», «регламент» — только архитектурная модель,
  в базу данных не входят.
